# 第七阶段方向建议（提案，待确认）

> 依据：2026-11-17 实际检查的代码、数据库与运行状态。本文只做方向建议，不含实现。
> 结论：推荐以「运营闭环」为主线进入第七阶段，先补数据基础（分类、评价、审计），再做订阅与告警，最后收敛权限。

## 1. 现状核查（真实证据）

已具备（前六阶段）：

- 工单全生命周期：创建 → 分配 → 接受 → 处理 → 解决 → 关闭 / 取消，状态机 + `ticket_events` 流转记录。
- SLA：仅响应时限（4/8/24/72 小时），无独立解决时限字段。
- 智能调度：推荐 + 分配日志（`dispatch_logs`），技能匹配。
- AI：分析/优先级/方案/调度辅助/问答，建议需人工确认。
- 分析中心：6 个页面、13 个接口，SQL 实时聚合。

当前真实缺口（影响下一阶段选型）：

| 缺口 | 证据 | 影响 |
| --- | --- | --- |
| 无工单分类字段 | `tickets` 仅 `type`（INCIDENT/SERVICE_REQUEST/CHANGE/CONSULT） | 分析中心只能按类型统计，无法做问题分类治理 |
| 无满意度/评价 | `tickets` 无评价列，库中无评价表 | 服务质量只有时效，没有结果质量 |
| 无通知/订阅 | 库中无 notification / subscription 表 | 分析结果只能人肉查看，无法主动触达 |
| 无审计日志 | 库中无 audit 表，操作仅靠业务表时间戳 | 权限变更、SLA 调整、建议采纳不可追溯 |
| 权限粒度过粗 | 仅 ADMIN / USER / AGENT 三角色，接口内硬编码判断 | 无法按团队/职能细分 |
| 调度数据不完整 | `dispatch_logs.RECOMMEND.agent_id` 为 NULL，无负载快照 | 采纳率无法判定，已按 unverifiable 处理 |
| 文档滞后 | `README.md` 仍写「第一阶段/尚未包含工作流与 AI」 | 新人接手会误判项目状态 |

## 2. 三个候选方向

### 方向 A：运营闭环（推荐）
把「能看」变成「能管」：分类体系 → 满意度 → 告警订阅 → 审计。直接补齐上面 4 个数据缺口，让第六阶段的分析有治理动作可落地。

### 方向 B：自助服务门户
面向普通用户开放 AI 问答 + 知识库检索 + 自助提单，减少人工工单。价值高，但依赖知识库内容质量，且需要先解决权限细分（当前 USER 角色几乎无页面）。

### 方向 C：工程质量与性能
CI、端到端测试、压测、可观测性。当前 153 个后端单测、无 E2E、数据量小（21 工单），性能问题尚未真实出现，属于「预防性投入」。

## 3. 推荐方案：方向 A（运营闭环）

### 3.1 模块与优先级

**P0｜工单分类体系（数据基础）**
- 新增 `ticket_categories`（两级：id、parent_id、code、name、sort、enabled）与 `tickets.category_id`（可空，回填不猜测）。
- 历史数据回填策略：只按 `type` 建立 1:1 映射（如 INCIDENT → 故障），**不自动编造二级分类**；未回填的保持空并在分析页显示「未分类」。
- 分析中心「分类分析」从类型升级为真实分类；分类树筛选进入工单列表与报表。
- 验收：分类可维护；工单可设置分类；分析页分类分布与数据库一致；未分类单独统计。

**P0｜满意度评价（CSAT）**
- 新增 `ticket_feedback`（ticket_id、score 1-5、comment、created_by、created_at，唯一 ticket_id）。
- 关闭/解决后由创建人评价；评价只读、不可改（或限时修改，需你决策）。
- 分析新增「服务质量」小节：平均分、评分分布、低分（≤2）工单清单与类型/人员关联。
- 验收：评价只能由创建人提交一次；分析口径明确（平均分分母 = 已评价工单）；低分工单可下钻。

**P1｜报表订阅与阈值告警**
- 新增 `report_subscriptions`（报表类型、筛选条件、频率、收件人、启用）与 `notifications`（站内通知）。
- 定时任务：按频率生成报表并写站内通知；阈值规则（如 SLA 达标率 < X、超时数 > N）触发告警。
- 外部通道（邮件/飞书）先留接口，默认关闭，避免引入不稳定依赖。
- 验收：订阅可增删改停；到点生成通知；阈值触发可复现；无数据不乱报。

**P1｜审计日志**
- 新增 `audit_logs`（actor、action、target_type、target_id、before/after JSON、ip、created_at）。
- 覆盖：工单状态流转、SLA 参数变更、人员与技能变更、AI 建议采纳/拒绝、报表导出。
- 只读审计页（ADMIN），支持按人/动作/时间筛选。
- 验收：关键动作 100% 落日志；不含敏感字段；页面可查。

**P2｜权限细分**
- 引入权限点（如 `ticket:assign`、`sla:config`、`analytics:view`、`audit:view`），角色→权限矩阵存库。
- 保持现有三角色默认行为不变，避免破坏前六阶段。
- 验收：既有接口行为不回退；新权限点可配置；USER 无法越权。

**P2｜文档校准**
- 更新 `README.md` 到第六阶段真实现状，并补启动/验收入口。

### 3.2 不在本阶段范围

- 不引入 Redis / 消息队列 / 数据仓库（数据量与场景不构成依据）。
- 不做多租户。
- 不补「解决 SLA 时限」字段，除非你明确要调整 SLA 模型（会影响历史口径）。
- 不伪造历史分类与评价数据。

### 3.3 风险与依赖

| 风险 | 应对 |
| --- | --- |
| 分类回填改变分析口径 | 旧 `type` 统计保留，分类统计新增字段；页面标注口径差异 |
| 评价率过低导致指标失真 | 页面同时展示「已评价数/已关闭数」，样本不足提示 |
| 定时任务与单实例部署冲突 | 先用 Spring `@Scheduled` + 数据库锁标记，不引调度中间件 |
| 审计日志膨胀 | 按月归档表，查询默认限最近 90 天 |

## 4. 备选方案的取舍理由

- 方向 B 的自助门户收益大，但当前 USER 角色页面缺失、知识库文章量未知（`kb_articles` 需先核查内容量），直接做会先卡在权限与内容上；建议排在方向 A 之后。
- 方向 C 的压测与 CI 在当前数据规模下难以暴露真实问题，可作为方向 A 的并行小项（先把 README 校准、补一条 E2E 冒烟）。

## 5. 需要你决策的三件事

1. 是否采用方向 A 的 P0 两项（分类体系 + 满意度）作为第七阶段第一批？
2. 满意度评价是否允许创建人在限时内修改（影响表结构与接口设计）？
3. 告警外部通道是否本期就要接（邮件/飞书），还是先只做站内通知？

确认后我会按既有流程执行：先审计（`docs/phase7-audit.md`）→ 指标与接口设计 → 开发 → 联调 → 测试报告。
