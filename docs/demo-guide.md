# 第七阶段：项目演示指南

> 演示数据即当前 `serviceflow` 数据库中的真实数据（21 张工单、5 个用户、14 张业务表），所有页面调用真实接口，无 Mock、无伪造返回。
> 权限校验全程生效，不提供「跳过登录」的演示开关。
> 标注「需 Key」的步骤依赖 Python 服务已配置 `DEEPSEEK_API_KEY`；未配置时按第 3 节降级演示。

## 2. 演示脚本（12 步）

### 步骤 1：管理员登录

- 页面：登录页 → 输入管理员账号密码 → 登录。
- 后端：`POST /api/auth/login`，返回 JWT 与用户信息，角色 `ADMIN`。
- 讲解点：密码 BCrypt 校验；Token 由 `JwtService` 签发；登录接口是唯一公开的业务接口。

### 步骤 2：创建一张工单

- 页面：工单中心 → 工单列表 → 新建。
- 填写：标题、描述、优先级（选择 `HIGH`）、分类。
- 期望：列表新增一条 `OPEN` 状态的工单；详情中出现 SLA 截止时间（HIGH 为 8 小时）。
- 讲解点：创建时由 `TicketSlaService` 依据配置 `sla.policy.high-hours` 计算并持久化 `sla_due_at`；插入 `tickets` 并写一条 `ticket_events`（CREATE）。

### 步骤 3：查看工单详情

- 页面：点击刚创建的工单。
- 期望：基本信息、SLA 倒计时/进度、流转时间线、AI 建议区（空）、关联知识（空）。
- 讲解点：详情由工单 + 事件 + 建议聚合返回；时间线来自 `ticket_events`，不是前端拼装。

### 步骤 4：执行状态流转

- 操作：分配到某处理人 → 处理人接单 → 开始处理。
- 期望：状态依次变为 `ASSIGNED` → `IN_PROGRESS`，每次操作在时间线新增一条事件，记录操作人。
- 异常演示：对 `IN_PROGRESS` 的工单再次点「接单」，后端返回 409，前端提示状态已变更。
- 讲解点：合法动作由 `TicketWorkflowEngine` 白名单校验，非法流转在服务层被拒绝。

### 步骤 5：展示 SLA 计算

- 页面：工作流 → SLA 管理。
- 期望：URGENT/HIGH/MEDIUM/LOW 分别 4/8/24/72 小时，预警阈值 120 分钟。
- 讲解点：时限来自 `sla.*` 配置，修改环境变量重启后接口同步变化；剩余时间 ≤120 分钟显示 WARNING，<0 显示 OVERDUE；完成态记录「按时/超时完成」。

### 步骤 6：查看人员负载

- 页面：智能调度 → 人员负载。
- 期望：每位处理人的进行中工单数、负载等级（低/正常/高/饱和）、技能标签。
- 讲解点：负载由工单实时聚合，不是缓存快照。

### 步骤 7：展示规则调度结果

- 页面：智能调度 → 调度工作台 → 选择待调度工单 → 生成推荐。
- 期望：Top5 候选人及四维得分（技能/负载/SLA/绩效）与总分，可看到推荐理由。
- 讲解点：权重来自 `dispatch.weights`；候选先按技能与可用性过滤；确认分配时用数据库条件更新避免同一工单被重复分配（可开两个窗口同时点击验证）。
- 异常演示：两个浏览器同时分配同一工单，只有一个成功，另一个返回冲突提示。

### 步骤 8：使用 AI 分析工单（需 Key）

- 页面：AI 智能中心 → AI 工作空间 → 选择步骤 2 的工单 → 发起「工单分诊」。
- 期望：数秒后返回分类、优先级建议、处理方案、知识推荐；页面显示模型与耗时。
- 未配置 Key 时：返回 503 与错误码 `AI_CONFIG_MISSING`，页面提示「AI 服务未配置」，其余功能不受影响。
- 讲解点：Java 只转发结构化上下文，Key 只在 Python；调用带 `X-Request-Id`，可在两侧日志按同一 ID 查到耗时；结果经 Pydantic 严格校验后才入库。

### 步骤 9：展示 AI 处理建议

- 页面：工单详情 → AI 建议区，或 AI 分析详情。
- 期望：建议条目包含类型、内容、置信度、状态（待确认）。
- 讲解点：建议与工单分离存储，AI 不能直接修改工单；Prompt 把工单内容包在 `<untrusted_data>` 中，降低注入风险。

### 步骤 10：检索知识库

- 页面：知识库 → 输入关键词（如「网络」「打印机」）→ 搜索。
- 期望：命中条目、分类筛选、关联工单数；可在工单详情中看到推荐知识。
- 讲解点：关键词与分类均参数化查询；AI 知识推荐只是候选，需人工关联。

### 步骤 11：人工采纳建议

- 页面：AI 建议 → 采纳（可编辑后采纳）。
- 期望：建议状态变为「已采纳」，工单字段（如优先级/分类）按建议更新，时间线新增事件；建议驳回则只改状态。
- 讲解点：采纳前再次校验操作者是否有权访问该工单；采纳动作是唯一允许 AI 内容写回业务的入口。

### 步骤 12：查看数据分析报表

- 页面：数据分析 → 工单运营分析 / SLA 效率分析 / 人员绩效 / 智能调度 / AI 效果 / 综合报表。
- 期望：图表数据与前面操作的工单一致；综合报表可导出 CSV。
- 讲解点：分析接口有区间与跨度上限校验；报表导出使用同一聚合口径，不重复计算。

## 4. 建议的异常场景

| 场景 | 操作 | 期望 |
| --- | --- | --- |
| 未登录访问 | 退出登录后刷新页面 | 跳转登录页；接口 401 |
| 越权查看 | 用 USER 账号访问他人工单详情 | 403，不返回工单内容 |
| 非法流转 | 对已关闭工单执行「开始处理」 | 409 + 明确文案 |
| 重复分配 | 两个窗口同时确认同一工单 | 一个成功、一个冲突 |
| AI 超时 | 断开 Python 服务后发起分析 | 502/504 + `X-AI-Error-Code`，工单功能不受影响 |
| 数据库异常 | 停止 MySQL 后访问 ready | 503，`mysql: DOWN`，其余接口报数据库错误但进程不崩溃 |
| 会话失效 | 退出登录后用旧页面发起写操作 | 401，前端清理用户缓存并回到登录页 |
| CSRF 防护 | 删除 `sf_csrf` Cookie 后发起写操作 | 403，提示刷新页面后重试 |

## 5. 演示注意事项

1. 不要删除演示工单，后续报表口径依赖历史数据。
2. 演示 AI 前先确认服务状态，避免现场等待超时；超时时间最长 90 秒。
3. 不展示 `.env`、日志中的连接串或任何密钥。
4. 若在旧进程上演示（未重启到第七阶段代码），Swagger、请求 ID、ready 中的 AI 组件不可用，需先按 `docs/deployment-guide.md` 重启。
5. 每一步都可停留讲解对应表结构：`tickets`、`ticket_events`、`dispatch_logs`、`ai_analyses`、`ai_suggestions`、`knowledge_articles`。

## 6. 演示后核对（数据库）

```sql
SELECT id, ticket_no, status, priority, sla_due_at FROM tickets ORDER BY id DESC LIMIT 5;
SELECT id, ticket_id, action, from_status, to_status, operator_id FROM ticket_events ORDER BY id DESC LIMIT 10;
SELECT id, ticket_id, agent_id, action, created_at FROM dispatch_logs ORDER BY id DESC LIMIT 10;
SELECT id, ticket_id, analysis_type, status, cost_ms FROM ai_analyses ORDER BY id DESC LIMIT 10;
SELECT id, analysis_id, status, adopted_by FROM ai_suggestions ORDER BY id DESC LIMIT 10;
```

期望：页面上的每次操作都能在对应表中找到记录，且时间顺序一致。
